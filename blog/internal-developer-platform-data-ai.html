Designing an Internal Developer Platform for Enterprise Data & AI

Consolidating mature platform capabilities into one configuration model, workflow-driven delivery, and secure golden paths.

This architecture did not start with a blank sheet. It followed the batch model-serving platform, application-isolated MLflow registry, and real-time model-serving platform that I had led as architect. Each had matured independently and accumulated useful patterns around self-service, security, delivery, and operations.

The first article in this series covers those original platforms. This article focuses on the next phase: consolidating their shared foundations into an Internal Developer Platform without erasing their domain-specific interfaces or ownership.

Evolution to an Internal Developer Platform

The consolidated platform began only after the earlier platforms had evolved through multiple iterations. Repeated patterns across infrastructure, delivery, security, and operations made a shared foundation practical. The goal was not one oversized platform. The IDP consolidated the developer experience beneath existing capabilities: self-service, composable infrastructure, delivery standards, security controls, and operational guardrails.

The technology catalog includes Databricks, AzureML, Azure Container Apps, Azure App Service Web Apps, Azure AI Search, and other services selected according to the workload. Delivery is workflow-driven rather than tied to one infrastructure tool.

Components, Workflows, and Deploy

  1. Components: Reusable blueprints and building blocks, including Pulumi components, bundle templates, and platform CLIs.
  2. Workflows: Capability-specific pipelines that execute ordered validation and deployment steps.
  3. Deploy: Environment-specific configuration and pipeline entry points that select and run the appropriate workflow.

A workflow might validate and deploy a Databricks Declarative Automation Bundle with the Databricks CLI, invoke our AzureML CLI, execute pulumi up for a project, or coordinate several actions. The workflow is the stable platform interface; the implementation tool remains a capability-level decision.

Components and workflows are semantically versioned. Development can consume a newer version while production remains stable, and temporary alpha spokes can validate changes without affecting existing workloads. Renovate helps roll component and workflow updates forward safely.

Monitoring as a Platform Capability

Infrastructure health is only one part of production analytics. We introduced model portals where users could inspect logs, create dashboards, and configure alerts without waiting for a platform engineer. We also explored Lakehouse Monitoring as a configurable workspace capability integrated with the wider data ecosystem.

Questions around evidence retention, champion and challenger comparison, intermediate-data traceability, and governed model chains helped shape storage and metadata boundaries. New technology such as MLflow 3 is valuable only when it addresses a validated platform need.

GenAI and Agentic Systems

We introduced a RAG blueprint in which Databricks handles chunking and embedding while Azure AI Search provides vector retrieval. Declarative indexing configuration replaced fragile implementations based on manually parsed documents and hard-coded page ranges.

The design separated indexing, centrally managed middleware and authentication, and the user interface. For custom agentic workloads, Azure Container Apps can host LangChain or LangGraph code exposed through Kong. We also investigated an AI Gateway for centralized policy, routing, observability, and cost control.

The Four-Layer Platform Architecture

  1. Global Layer: Hub networking, firewalls, DNS resolvers, cross-organization private endpoints, and a hub-owned Azure Front Door entry point.
  2. Subscription Vending: An application spoke with networking, Key Vault, Log Analytics, and Azure Container Registry.
  3. PaaS Self-Service: A catalog through which teams select Databricks, AzureML, AI Search, and other managed capabilities.
  4. Workload Workflows: Delivery pipelines connecting application configuration, code, and models to the appropriate capability tools.

The resulting design is private by default. Managed services communicate through private endpoints, subnet boundaries, network security groups, and centralized firewall policy. Workload identities receive least-privilege access, and secrets reach compute through Key Vault-backed integrations.

Azure Front Door centralizes custom domains, TLS, Web Application Firewall policy, health-aware routing, and global traffic distribution for applications that need a governed public edge.

From Components to a Product Operating Model

The next iteration treats the platform as a product rather than a collection of infrastructure components. Its portal-driven golden paths combine clear ownership, supported delivery flows, operational integration, and Azure Well-Architected guardrails.

A shared service-management model connects applications and subapplications to ownership, lifecycle, impact analysis, and operational responsibilities. Architecture decisions remain visible through ADRs and are revisited as implementation evidence arrives.

Application Configuration and Reconciliation

Each registered application receives a workload-configuration repository as the source of truth for its intended state. It stores application metadata and environment-specific capability configuration—not shared infrastructure or full application source code.

application configuration repository 
application-config/
├── metadata/
│   └── application.yaml          # Application identity and ownership
├── environments/
│   ├── test/
│   └── production/
│       ├── databricks-resources/ # Declarative Automation Bundle resources
│       ├── azureml-endpoints/    # Real-time model endpoints
│       ├── container-apps/       # Containerized applications
│       └── web-apps/             # Web-facing applications
└── pipelines/
    ├── validate.yaml             # Pull-request checks
    └── deploy.yaml               # Deployment requests after merge

Environment folders favor fully hydrated, WET configuration: repetition is acceptable when it makes the exact desired state directly reviewable. Pull requests validate metadata, configuration, deployment assets, and capability contracts.

After merge, automation identifies changed workloads and starts the matching capability workflow at the immutable commit. Databricks workflows deploy bundles, real-time workflows invoke the AzureML CLI, and infrastructure steps can run Pulumi projects. Each reports status through the same GitOps experience.

Architecture Is Also an Operating Model

The platform did not scale through technology alone. Docs-as-code decision logs recorded context, alternatives, ownership, and consequences. Reusable components were paired with mentoring, demonstrations, developer sessions, and incremental transfer of ownership.

These social interfaces matter as much as APIs: a design becomes a platform capability only when other teams can understand, operate, and extend it safely.

Extending the Golden Path

Backstage could become the front door, combining workload ownership, documentation, APIs, dependencies, operational links, and scaffolding. Its actions can create pull requests, start workflows, or invoke platform CLIs without replacing capability-specific delivery.

Argo CD can add a Kubernetes path for workloads that need it, while the Pulumi Kubernetes Operator can reconcile cloud infrastructure and Kubernetes resources together. These are additional workflow implementations—not competing configuration models.

Final Thoughts

Workflow-driven delivery lets the platform scale without forcing every capability into one tool. Databricks bundles, platform CLIs, Pulumi projects, and other mechanisms sit behind consistent workflows and automated gates. Product teams receive a cloud-native experience while security and compliance remain part of the paved road.

The next frontier is application code itself: standardized scaffolds can help teams start right and stay right. In enterprise engineering, the best platform is not only about technology—it is about the interface provided to developers.
