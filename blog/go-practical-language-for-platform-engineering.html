When CI/CD Scripts Become Software: Why Go Is Worth Considering

Bash, PowerShell, and Python are excellent ways to automate delivery. As that automation grows and serves more teams, Go can offer an interesting next step.

pipeline.yml

scripts/→platformctl

A declarative pipeline backed by a small, tested, versioned executable.

Most delivery automation begins innocently: five lines of Bash to upload an artifact, a PowerShell function to configure an Azure resource, or a Python script to call three APIs. It works, so it grows. Soon it validates policy, chooses environments, retries requests, transforms JSON, handles credentials, coordinates deployments, and determines whether production is healthy.

Over time, the surrounding environment becomes part of the system too: shell behavior, modules, interpreter versions, packages, command-line tools, and build-agent configuration. Containers and dependency locking can manage this well. Another option is to package more of that behavior into a compiled tool with a clearly versioned interface.

A useful script can gradually become a shared product. Recognizing that transition opens up new design options.

This is not a call to rewrite every script. Small, local scripts are often exactly right. I am interested in the point where automation becomes a shared delivery contract. At that boundary, Go has a combination of qualities that is well worth exploring.

From a useful script to a shared tool

Bash and PowerShell are natural starting points. They are already on the runner, they compose existing commands directly, and a short script is easy to inspect. Python gives the same automation room to grow into functions, richer data handling, and direct use of cloud SDKs. Go adds another possibility when the result starts to feel like a shared delivery capability: package the contract, implementation, and runtime into one versioned executable.

Bash connects a few commands, Python offers a rich toolkit, and Go makes it appealing to package the result as a product.

Bash and PowerShell remain excellent for focused automation. Wrappers and short compositions of tools such as tar, ssh, or a cloud CLI are easy to understand in their native shell. As state, string processing, arrays, cleanup, and multi-step error handling accumulate, a team may simply find that a general-purpose program is easier to evolve. PowerShell’s object pipeline provides especially useful structure on Windows.

Python can take delivery automation a long way. Pydantic, tests, type checking, linting, locked dependencies, and thoughtful packaging can produce robust tools. Go becomes interesting when reducing the consumer-side environment is important. More responsibility moves to the producer, who builds and verifies the tool once, while users receive the resulting artifact.

Go offers an inviting production shape. It catches unused imports and variables, keeps errors visible, builds and starts quickly, and commonly produces a self-contained executable. The maintainer writes a little more structure up front; pipelines and developers receive something pleasantly straightforward to run.

Making room for a different kind of workload

Most enterprise “approved language” lists were designed around business applications: customer-facing services, mobile applications, web front ends, and large domain systems. That is a sensible governance boundary, but it leaves a gap. CI/CD glue code, internal CLIs, developer automation, and infrastructure tooling have a different lifecycle and a different distribution problem.

Applying an application-language standard unchanged to delivery tooling can leave teams without an option designed for this workload shape. A small, scoped extension to the standard could make Go available for:

  • CI/CD orchestration that has outgrown embedded scripting;
  • internal command-line tools used by multiple teams;
  • developer-facing automation and platform engineering;
  • infrastructure tooling that must run frequently and consistently across environments.

The existing choices for business applications can remain unchanged. A cross-platform CLI invoked in many pipelines simply has a different set of needs from a banking API, a mobile app, or a data-science notebook.

A useful governance principle

Support the language together with its operating model. A good Go paved road could include code scanning, dependency governance, artifact publishing, signing, software bills of materials, pipeline templates, builder images, vulnerability checks, and clear ownership. That turns permission into a genuinely useful developer experience.

The appeal of deliberate practicality

The usual language debate starts with features: which language is fastest, has the richest type system, or feels most expressive? Those questions matter, but platform engineering has a different unit of success: can a team build, review, deploy, and operate this tool confidently six months from now?

That is the terrain Go was designed for. Born at Google in response to the friction of large software systems, Go optimizes the system around the code: compilation, collaboration, deployment, concurrency, and operations. It does not try to offer every abstraction or win every microbenchmark. It makes a focused trade: less language surface and some runtime overhead from garbage collection in exchange for productive development, native compilation, efficient execution, and a simple operational model.

For many tools, Go finds a useful balance between productivity and performance: enough speed for demanding work, with an emphasis on making software approachable to build, understand, ship, and operate.

Operational excellence: The "Scratch" container

One of Go’s most powerful operational features for Platform Engineers is the ability to build statically linked binaries. By disabling CGO (CGO_ENABLED=0), the Go compiler includes all necessary libraries directly into the executable, removing any dependency on the host's C library.

Dockerfile for a Go tool
FROM golang:1.23-alpine AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 go build -o platformctl .

FROM scratch
COPY --from=builder /app/platformctl /platformctl
ENTRYPOINT ["/platformctl"]

Using the scratch image—a special, completely empty Docker image—provides several critical advantages for delivery infrastructure:

  • Minimal Attack Surface: There is no shell, no package manager, and no unnecessary binaries. An attacker who finds a vulnerability in your code has no built-in tools to use for lateral movement.
  • Extreme Portability: Images are often under 15MB. This results in near-instantaneous container pulls and significantly lower storage costs across your registries.
  • Zero OS Maintenance: Since there is no operating system inside the container, you never have to patch "base image" vulnerabilities or worry about OS-level library drift. Your security focus stays entirely on your own code and its dependencies.

Where Go sits among other languages

Compared with Bash and PowerShell, Go requires more structure up front but scales better into a tested, versioned program. Compared with Python, it gives up some interactive speed and ecosystem convenience to remove the interpreter and application environment from distribution. Compared with Java and C#, it offers a smaller language and a simpler executable-first deployment model, although it is not automatically faster in raw throughput. Mature JVM and .NET runtimes can equal or outperform Go for some workloads. Compared with C and C++, Go accepts garbage collection and less low-level control in return for memory safety, faster development, and far less manual resource management.

That position helps explain why Go often appears in infrastructure and delivery tooling. A CLI may value quick startup, modest resource use, straightforward networking, cross-compilation, and approachable source code more than either maximum low-level performance or a broad application framework.

The first impression can be misleading

Go can look old-fashioned beside feature-rich languages. There are no classes, exceptions, traditional enums, pattern matching, decorators, method overloading, operator overloading, or implicit type conversions. The repeated if err != nil can feel verbose. Developers may initially interpret this as a language that stopped short of modern features.

Those omissions are largely part of the design. Go tries to keep the number of ways to express ordinary control flow small. Composition through structs and interfaces takes the place of inheritance. Errors remain values in the visible execution path. Garbage collection removes manual memory management. This style will not suit every team, but it can make unfamiliar code surprisingly quick to navigate.

The same idea appears in gofmt. Formatting is not a repository-wide negotiation, a linter preset, or a review comment. There is a canonical answer. This sounds small until a project has dozens of contributors, automated changes, and code produced by coding agents.

One of Go’s nicest qualities is how often unfamiliar code still looks familiar.

This restraint matters for shared delivery tooling. Pipeline code is read during reviews, incidents, migrations, and handovers. Its value comes less from elegant abstraction than from making the next effect—and the next possible failure—obvious.

There is also plenty to learn from existing Go projects in this domain. Docker, Kubernetes, and Terraform are prominent examples. They do not imply that every pipeline helper belongs in Go, but they have helped create a mature ecosystem and a large body of experience around cross-platform infrastructure software.

Signals that a shared CLI might help

Line count alone says little. A 300-line one-off migration script may be perfectly fine, while a 30-line script included by 200 repositories may deserve more structure. It may be worth experimenting with a supported CLI when several of these are true:

  • Multiple repositories or teams depend on it.
  • It changes production state or enforces delivery policy.
  • It needs retries, timeouts, concurrency, rollback, or idempotency.
  • Linux and Windows implementations have started to drift.
  • Inputs are mostly undocumented environment variables.
  • Tests require mocking a shell, a filesystem layout, and several installed CLIs.
  • A change must be coordinated—or can break every consumer at once.
  • Failure output is meant for both people and pipeline logic.

In practice, this automation already behaves like an API: environment variables are parameters, console text is a response model, and exit codes form an error protocol. A CLI offers an opportunity to make that existing contract more visible and deliberate.

What Go can simplify

1. The runner can receive a ready-to-use artifact

A Go program is commonly delivered as a single executable containing the application code and Go runtime. Build it once for your supported operating systems and architectures, publish checksums and signatures, and let pipelines pin a version. The release job downloads platformctl v1.8.3; it does not resolve packages from the network and hope today’s environment matches yesterday’s.

Build once, promote the same artifacts
GOOS=linux   GOARCH=amd64 go build -trimpath -o dist/platformctl-linux-amd64 ./cmd/platformctl
GOOS=windows GOARCH=amd64 go build -trimpath -o dist/platformctl-windows-amd64.exe ./cmd/platformctl
GOOS=darwin  GOARCH=arm64 go build -trimpath -o dist/platformctl-darwin-arm64 ./cmd/platformctl

This is not magic. CGO and native libraries can complicate static linking and cross-compilation. Certificates, credentials, and configuration still exist. But for API-oriented delivery tools written with pure Go dependencies, the default deployment surface is refreshingly small.

2. The contract travels with the artifact

Python already has excellent ways to validate data. Pydantic can model configuration, identify missing fields, constrain values, and produce useful diagnostics. Type checkers, locked environments, and packaging tools can make Python delivery code robust. Bash and PowerShell can likewise validate required variables before doing work.

Go’s advantage is cumulative rather than exclusive: configuration structs, command options, interfaces, implementation, and compilation live in one consistently checked toolchain, and the resulting contract is shipped inside the executable. Changing a field or interface identifies affected call sites during the build. More importantly, consumers do not need the source environment, Pydantic version, type checker, interpreter, or package resolver to run the validated program.

Compilation does not prove that a deployment is correct, and static typing is not the reason by itself to rewrite working Python. It is one part of a broader operational shape: validate once, test once, build once, and promote the same immutable artifact.

3. Testing fits naturally around ordinary functions

Command parsing can stay at the edge while delivery behavior lives in ordinary functions. Policy checks can be table-tested. HTTP dependencies can use test servers. Filesystems and command execution can sit behind narrow interfaces. Integration tests can exercise the compiled CLI and inspect stdout, stderr, and exit codes.

The CI loop for the delivery tool itself
gofmt -w .
go vet ./...
go test ./...
go test -race ./...

Black-box compatibility testing is a reassuring way to explore a migration: describe what the current script does from the outside, then run the same cases against the new implementation. Flipp used this approach while replacing Bash deployment scripts with Go, preserving observable behavior while changing the implementation underneath.

Why the feedback loop also works well with coding agents

Go does not make AI-generated code correct, but it provides a friendly verification loop. gofmt removes mechanical uncertainty, while the compiler gives precise feedback about types, assignments, imports, methods, and interfaces. Fast builds make it practical to repeat that loop after every change.

The language also offers fewer competing patterns than many general-purpose languages. Conventions for errors, HTTP, JSON, tests, flags, and cancellation are widely recognizable. That narrows the space of plausible implementations and reduces formatting noise in generated diffs.

Consistency still needs judgement

Compilation cannot tell us whether a retry is safe, a log reveals a secret, or a concurrency limit is sensible. Coding agents work best when a task also describes timeouts, cancellation, redaction, authorization, and destructive operations. The tooling creates a helpful feedback loop; thoughtful review remains essential.

4. Failures can become data

Stable exit codes and structured results can make failures easier to work with. A CLI can distinguish invalid input, authentication failure, policy rejection, and a platform timeout; write diagnostics to stderr; emit JSON to stdout; redact secrets; and include a correlation ID.

A machine-readable deployment result
{
  "status": "failed",
  "application": "payments-api",
  "environment": "production",
  "correlationId": "9bd40e03-9ef6-4b14-88bf-d961cd4122e8",
  "error": {
    "code": "POLICY_VALIDATION_FAILED",
    "message": "Production deployments require two deployment owners."
  }
}

Go’s repetitive if err != nil becomes useful here. At each boundary there is a visible opportunity to add context, retry, translate the error, or stop. The repetition can feel worthwhile when it produces clearer operational behavior.

A useful Go review question

“If this dependency fails at 02:00, does this code preserve enough context for the next engineer to understand what happened and what to do?”

5. Concurrent work can keep its cancellation path

Delivery tools often wait on independent operations: checking regions, validating repositories, querying deployment status, or uploading artifacts. Goroutines make that work inexpensive to express. The production value is not “millions of goroutines”; it is that concurrency can have a clear owner, bounded lifetime, and cancellation story through context.Context.

Bounded concurrent validation
func ValidateAll(ctx context.Context, targets []Target) error {
    group, ctx := errgroup.WithContext(ctx)
    group.SetLimit(8)

    for _, target := range targets {
      target := target
      group.Go(func() error {
        if err := validateTarget(ctx, target); err != nil {
          return fmt.Errorf("validate %s: %w", target.Name, err)
        }
        return nil
      })
    }
    return group.Wait()
  }

A real implementation still needs timeouts, metrics, retry policy, and idempotency. Go does not remove those choices. It gives them a small, visible vocabulary and a race detector with which to challenge the implementation.

A smaller role for pipeline YAML

I like pipeline YAML most when it describes the workflow: stages, dependencies, approvals, environments, service connections, and artifact promotion. As conditionals, embedded shell, string interpolation, and vendor-specific expressions accumulate, moving some behavior behind a CLI can make the pipeline easier to read.

A deliberately thin pipeline step
- script: |
    ./platformctl deploy \
      --config deploy.yaml \
      --environment production \
      --output json \
      --non-interactive
  displayName: Deploy application

This creates a useful division of responsibility. The CI/CD product can continue to manage identity injection, approvals, stages, and environment gates. The Go tool can focus on validation, orchestration, API calls, timeouts, retries, idempotency, redaction, and output. The same executable may then run on a laptop, in a pull request, and in a release job.

Stable service APIs or SDKs can improve control and testability. Calling a vendor CLI can be equally pragmatic; wrapping that interaction in one package, pinning its version, and capturing stdout, stderr, and exit status keeps the dependency easy to see.

A small boundary can be enough

Adopting Go does not need to begin with a fleet-wide rewrite. A useful boundary can be much smaller: a command that depends on a local environment, a release step assembled from several scripts, or a service coordinating managed cloud APIs. One focused tool is enough to learn whether the approach helps.

An example: from script bundle to platformctl

Imagine reusable scripts that validate configuration, upload a Databricks wheel, deploy an App Service package, update an Azure AI Search index, and publish a release summary. Rather than translating every line, the first interesting step is to understand the contract that consumers already depend on.

The existing script bundle

  • Environment variables spread across templates
  • Human-oriented output consumed by pipelines
  • Shared scripts updated centrally
  • Separate .sh and .ps1 implementations
  • Partial success represented in logs

One possible CLI shape

  • Versioned configuration with schema validation
  • JSON output and documented exit codes
  • Pinned, signed CLI releases
  • Equivalent binaries from one codebase
  • Dry-run, idempotency, and correlation IDs

A simple internal structure might look like this:

Keep framework code at the edge
cmd/platformctl/       flags, stdin/stdout/stderr, exit codes
internal/config/       parsing and validation
internal/policy/       pure delivery rules
internal/deploy/       orchestration and idempotency
internal/platform/     Azure, Databricks, GitHub, Kubernetes clients
internal/result/       stable machine-readable output

Whether the CLI framework is Cobra, urfave/cli, Kong, or the standard flag package matters less than the boundary. Thin commands and ordinary business functions can keep the core behavior independent of the CI system that invoked it.

Cobra or Typer for an internal CLI?

Cobra and Typer can expose the same high-quality command contract. Typer derives the interface concisely from typed Python functions. Cobra makes the command hierarchy, flags, and execution wiring explicit in Go. The decision is less about which library is better than about where the workflow lives, who owns it, and how the artifact must be distributed.

cmd/platformctl/validate.go — Cobra
func newValidateCommand() *cobra.Command {
    var config, environment string

    cmd := &cobra.Command{
      Use: "validate",
      RunE: func(cmd *cobra.Command, _ []string) error {
        return validateDeployment(cmd.Context(), config, environment)
      },
    }
    cmd.Flags().StringVar(&config, "config", "", "Configuration path")
    cmd.Flags().StringVar(&environment, "environment", "", "Target environment")
    return cmd
  }
platformctl.py — Typer with Pydantic validation
from pathlib import Path
  import typer
  from pydantic import BaseModel

  class Deployment(BaseModel):
    application: str
    environment: str

  app = typer.Typer()

  @app.command()
  def validate(config: Path) -> None:
    deployment = Deployment.model_validate_json(config.read_text())
    validate_deployment(deployment)

The Python example is intentionally strong because Pydantic provides excellent runtime validation. Typer can be a lovely fit beside notebooks, model SDKs, MLflow, or Databricks code. Cobra becomes interesting when the CLI itself is a versioned, cross-platform capability that many teams will consume without needing its application environment.

A practical way to choose

Typer keeps a focused CLI close to an existing Python workflow. Cobra pairs naturally with a broadly distributed Go tool. Both can support thin commands, validation at the boundary, stable exit codes, non-interactive execution, and structured output.

Supply chain security by design

Go was built with the reality of large-scale dependency management in mind. For platform engineering, where tools often run with high privileges, this translates to a more predictable and secure delivery pipeline.

verifiedMinimal Version Selection

Unlike managers that resolve to the latest compatible version (risking "dependency drift"), Go prefers the oldest version that satisfies requirements. This makes builds extremely reproducible and prevents pipelines from breaking—or inheriting new vulnerabilities—unexpectedly.

securityBuilt-in Vulnerability Scanning

With govulncheck, Go provides an official, high-precision scanner. It doesn't just check your go.mod; it analyzes your code to see if you actually call vulnerable functions, drastically reducing "noise" in your security reports.

The Go toolchain also uses a global Checksum Database (sum.golang.org) to ensure that the dependencies you download today are bit-for-bit identical to those downloaded when the code was first written. This effectively blocks "dependency confusion" and "man-in-the-middle" attacks on your source code.

Where the existing tools still shine

A three-line wrapper probably needs no replacement. Python remains a natural companion to data-science and model workflows. PowerShell is excellent for focused Windows administration. The most promising Go candidates are the places where a new artifact removes more complexity than it introduces.

Turning approval into a welcoming paved road

Adding Go to an architecture standard is only a beginning. Teams benefit from training, examples, ownership conventions, and a supported path from source to trusted binary. Artifact repositories may need a release convention for platform-specific executables, while security and engineering systems need to recognize modules, scan source and dependencies, and retain evidence.

Expected benefits

  • Reproducible builds and immutable releases
  • Fast startup for frequently invoked tools
  • Consistent execution across supported platforms
  • Compiler-assisted maintenance and refactoring
  • Smaller runtime and container dependency surface
  • A clearer support boundary for shared automation

Helpful enablement

  • Upskilling and review experience
  • Approved builder images and pipeline templates
  • Module proxy and artifact repository integration
  • Source, dependency, license, and vulnerability scanning
  • Signing, checksums, provenance, and SBOM generation
  • Versioning, deprecation, ownership, and support policies

Many enterprise security platforms already understand Go source and dependencies, so this is often an integration exercise rather than a search for new tools. A standalone binary can be simple for consumers while still carrying good provenance, ownership, dependency information, and a clear vulnerability-remediation path.

Perhaps try one small boundary

The next time a shared pipeline script gains another retry loop, cloud API, platform-specific branch, or configuration input, it may be interesting to pause and ask:

Would this workflow become easier to share if it were a small, versioned program?

Sometimes the answer will still be Bash, PowerShell, or Python—and that is fine. In other cases, a small Go CLI may make the pipeline simpler, the behavior easier to test, and the artifact easier to distribute. That modest experiment is the case I hope this article encourages: not Go everywhere, but Go where its simplicity can remove friction for everyone who comes after.

Getting started: A bridge from other languages

If you are coming from Python, Bash, or PowerShell, the transition to Go is more about unlearning certain habits than mastering complex new syntax. Here is how to think about the move.

5 things Python has that Go doesn't (and why)

1. Classes and Inheritance

The Go way: Composition over inheritance. Use structs and interfaces. It avoids deep, fragile class hierarchies and makes code dependencies explicit.

2. Try/Except Blocks

The Go way: Explicit error returns. Every function that can fail returns an error. This keeps error handling in the main control flow rather than jumping to hidden handlers.

3. List Comprehensions

The Go way: Simple for loops. While slightly more verbose, they are easier to debug, set breakpoints in, and reason about for any developer reading the code later.

4. Decorators

The Go way: Higher-order functions. Instead of hidden @decorator syntax, you explicitly wrap functions. It makes the execution path transparent and easier to trace.

5. Dynamic Typing

The Go way: Static typing with Interfaces. You get compile-time safety (no more AttributeError at runtime) while still having the flexibility of "duck typing" through interfaces.

5 things Go does better than Python

  • Runtime Performance: Go is a compiled language that typically runs 10-100x faster than Python. For CLI tools, this means near-instant startup and faster execution of heavy tasks like log parsing or data transformation.
  • True Concurrency: Unlike Python's Global Interpreter Lock (GIL), Go's scheduler allows goroutines to use all available CPU cores simultaneously, making it ideal for parallel I/O and compute-heavy platform tasks.
  • Memory Efficiency: Go programs use significantly less RAM than equivalent Python processes. This is especially noticeable when running many small utility tools in resource-constrained environments like CI runners or sidecars.
  • Static Analysis & Safety: The compiler catches entire classes of bugs (like typos in variable names or incorrect types) before the code ever runs. In Python, these often only surface as runtime AttributeError or TypeError.
  • Zero-Dependency Distribution: Go compiles everything—including all libraries—into a single executable. You don't need a requirements.txt, venv, pyenv, or even a Python interpreter on the target machine.

5 things Go does better than Bash or PowerShell

  • Structured Data handling: Native support for JSON/YAML with types. No more fragile jq, sed, or complex string manipulation.
  • Built-in Testing: A first-class testing framework comes standard. Testing a CLI's logic is as easy as testing a library, without needing third-party shell-test tools.
  • Concurrency: Goroutines allow you to run tasks in parallel (like checking dozens of API endpoints) with built-in safety and cancellation via Context.
  • Deployment Simplicity: A single, static binary. You don't need to worry if the target machine has the right version of Python, PowerShell Core, or specific CLI tools.
  • Cross-Platform by Design: Write once, compile for Windows, Linux, and macOS. No more maintaining separate .sh and .ps1 versions of the same logic.
